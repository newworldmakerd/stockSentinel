## 3. 建议分批实现

### 第一批：收盘闭环

1. 人工确认成功后幂等触发日线任务，增加有截止时间的补偿检查。仍要求交易日、源匹配、收盘时间和人工确认，不能到点自动认定行情最终完成。
2. 区分早盘观察池与收盘选股批次，保留早盘昨日依据；收盘确认后生成当日依据的独立结果，供日报或次日使用。避免直接覆写早盘快照，使已发送推荐难以追溯。
3. 日报明确区分当日行情快照、日线依据日和扫描完成情况，不能因为标题是今天就让用户误以为选股也使用今日收盘。

### 第二批：数据准备和故障覆盖

4. 把可复用历史和指标准备移到盘后或开盘前；盘中优先分钟监控。保留已有缓存和断点续扫，先测冷启动与次日增量耗时，再决定资源隔离和并发额度。前复权历史可能修订，增量方案必须含历史修订和源一致性校验，不能只追加最新一行。
5. 对日线与全市场任务补充各自周期的失败/超时提醒和数据质量清单；不能直接照搬分钟任务的3轮阈值。进程、数据库和机器人离线需要独立健康检查及本机恢复机制，同一机器人离线时不能承诺通过它发送故障消息。

### 第三批：用户能直接看懂结果

6. 增加只读策略诊断工具，让群里可以查询“这只股票为什么没入池”“今天各条件筛掉多少只”。返回真实数据日期、命中项、未满足项和阈值差距，模型只解释工具结果。保留固定规则和每10分钟重复推荐；可附首次入池/持续观察/已转强标签。
7. 设置个人提醒后返回明确操作回执，并在模型后续回答失败时说明具体已完成哪项操作。常用只读查询可采用明确指令直达；如需提高群对话并发，应保留同用户顺序、有界队列、写操作校验及每消息一次写入限制。
8. 先建立信号回放和规则复盘，再讨论调参。包含复权、停牌、涨跌停、T+1、费用、数据缺口与样本外检验；不能只统计上涨样本或用未来信息形成候选。

可直接复核当前稳定性的只读SQL：

```sql
SELECT status, count(*) AS runs,
       round(avg(extract(epoch FROM finished_at-started_at))::numeric, 2) AS avg_seconds,
       max(failed_count) AS max_failed_stocks
FROM job_execution
WHERE job_name='INTRADAY_SCAN'
  AND started_at >= TIMESTAMPTZ '2026-10-21 13:12:29+08'
  AND status<>'RUNNING'
GROUP BY status;

SELECT failure_kind, event_type, status, count(*)
FROM scan_fault_event GROUP BY failure_kind, event_type, status;
```

以上是候选方案，不是已实施变更。具体接口、迁移与可运行实现需在选定批次后另行设计，避免用未确认的契约替代现有行为。

## 4. 保留的校验和业务边界

- Java写库、调度和规则；Python仅行情和计算，不连接业务库。
- 当日日线人工确认、交易日历、最终收盘、来源与复权一致性、完整分钟和行情时效继续生效。
- 股票信号先由本地规则产生，模型只解释；规则和模型结果分开，失败不能改写规则事实。
- 个人提醒仍发当前群并标明所属用户，按回调真实用户隔离。
- 告警和股票通知保留UNKNOWN隔离、有限重试及防重；新增故障覆盖不能让提醒洪水淹没正常信号。
- 不自动下单、不自动添加推荐股票，不修改已执行Flyway迁移，不做多群改造。
